## ข้อห้ามเด็ดขาด — ผิดข้อใดข้อหนึ่งคือทำข้อมูลจริงพัง

1. **webapp/dev.db คือข้อมูลงานจริงของผู้ใช้ ไม่ใช่ข้อมูลตัวอย่าง**
   - สำรองก่อนแตะ schema ทุกครั้ง: `cd webapp && npm run backup`
   - ห้ามแก้/ลบแถวที่มีอยู่ · ห้าม reset · ห้าม seed ทับ
   - สร้าง user/ใบทดสอบเพื่อตรวจงานได้ แต่ **ต้องลบให้หมด**
     และตรวจว่าจำนวนแถวทุกตารางกลับมาเท่าเดิมก่อนปิดงาน

2. **migration ต้องเป็น additive ล้วน**
   - Prisma 7 ที่เครื่องนี้รัน `migrate dev` ไม่ได้ (non-interactive) ใช้สูตรนี้:
     ```bash
     cd webapp
     # หยุด dev server ก่อน — มัน lock dev.db
     TS=$(date +%Y%m%d%H%M%S); DIR="prisma/migrations/${TS}_approval_flow"; mkdir -p "$DIR"
     npx prisma migrate diff --from-migrations ./prisma/migrations --to-schema ./prisma/schema.prisma --script > "$DIR/migration.sql"
     ```
   - **เปิด migration.sql อ่านด้วยตาก่อนสั่ง deploy**
     ต้องมีแต่ CREATE TABLE / ALTER TABLE ADD COLUMN / CREATE INDEX เท่านั้น
     ถ้าเห็น DROP TABLE, DROP COLUMN, หรือ redefine ตาราง test_requests / test_items / users
     → **หยุด อย่า deploy แล้วรายงานผู้ใช้ก่อน**
   - แล้วค่อย: `npx prisma migrate deploy && npx prisma generate`

3. **ห้ามเปลี่ยนชื่อ/ลำดับสถานะ 1–8** (1-รับใบรีเควส … 8-ปิดงาน)
   สถานะอนุมัติเป็น **คนละแกน** อยู่ที่ระดับใบ ห้ามแทรกเข้าไปในลำดับนั้นเด็ดขาด
   (จะพัง rollup / analytics / CSV / QR ทั้งชุด)

4. **ห้าม commit ไฟล์เหล่านี้:** .env, *.db, dev.db.bak*, uploads/, node_modules, src/generated
   ก่อน commit ทุกครั้งให้เช็ค: `git diff --cached --name-only | grep -E "\.env|\.db|/uploads/|node_modules|src/generated"`
   ต้องไม่มีผลลัพธ์

5. **ห้าม deploy ขึ้น Railway หรือที่อื่น** โดยไม่ได้รับคำสั่ง — งานนี้จบที่ push ขึ้น GitHub

## กติกาการเขียนโค้ด
- UI/ข้อความทั้งหมด **ภาษาไทย** · ชื่อตัวแปร/ฟังก์ชัน/คอมเมนต์เชิงเทคนิค **อังกฤษ**
  (เขียนคอมเมนต์เท่าที่โค้ดรอบ ๆ เขาเขียนกัน อย่าใส่เยอะกว่าเดิม)
- เช็คสิทธิ์ **ฝั่ง server ทุก action เสมอ** ห้ามพึ่งการซ่อนปุ่มฝั่ง UI อย่างเดียว
  และห้ามพึ่ง proxy.ts อย่างเดียว (เอกสาร Next เตือนไว้เองว่า matcher เปลี่ยนแล้ว
  Server Function อาจหลุดการคุ้มครองเงียบ ๆ)
- ตัวกรองแผนกต้องเป็น "ชุด" ไม่ใช่ค่าเดียว: `requestDeptId: { in: ids }`
  เพราะหัวหน้า 1 คนคุมได้หลายแผนก (ดูข้อ 2.1.1 ในแผน)
- ใบของแผนกที่ไม่มีสิทธิ์ดู → ตอบ **404** ไม่ใช่ 403 (ไม่บอกว่ามีใบนั้นอยู่)

## วิธีทำงาน — ทีละเฟส หยุดรายงานทุกเฟส
ทำเรียงตามแผน 4a → 4b → 4c → 4d → 4e **จบแต่ละเฟสให้ทำครบ 4 อย่างนี้ก่อนไปเฟสถัดไป:**
1. `cd webapp && npx tsc --noEmit && npm run lint && npm run build` ต้องผ่านทั้งหมด
2. ตรวจด้วยการรันจริง ไม่ใช่แค่ compile ผ่าน (สร้าง user ทดสอบครบ role ที่เกี่ยวข้อง
   แล้วไล่เปิด route ตามตารางส่วนที่ 5 ในแผน) — เสร็จแล้วลบข้อมูลทดสอบให้หมด
3. commit แยกต่อเฟส ข้อความ commit เขียนว่า**ทำไม**ถึงแก้ ไม่ใช่แค่แก้อะไร
   ลงท้ายด้วย: Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
4. push แล้วสรุปให้ผู้ใช้อ่านสั้น ๆ ว่าเฟสนั้นได้อะไร เจอปัญหาอะไร แล้วค่อยไปต่อ

## จุดที่พลาดกันบ่อยในโปรเจคนี้ (อ่านไว้ก่อน จะได้ไม่เสียเวลา)
- `lib/roles.ts` ถูก import จาก client component → **ห้ามใส่ prisma / next/headers ในไฟล์นี้**
  (import type ได้ เพราะถูก erase ตอน build)
- `getCurrentUser()` ถูก `cache()` ต่อ 1 request แล้ว เรียกซ้ำได้ไม่เปลืองข้อมูล
- Server Action มีเพดาน body 1MB เป็นค่าเริ่มต้นของ Next — โปรเจคนี้ตั้ง
  `serverActions.bodySizeLimit` ไว้ใน next.config.ts แล้ว อย่าไปลบ
- ฟอร์มที่ส่งไฟล์ต้องใช้ `serverActions` ไม่ใช่ fetch เอง
- `redirect()` ในหน้าเพจส่ง meta-refresh + HTTP 200 (ไม่ใช่ 307) เวลาทดสอบด้วย curl
  ให้ดูใน body ว่ามี meta refresh ไหม · ส่วน proxy.ts ส่ง 307 จริง
- อย่าเชื่อค่าแผนกที่ส่งมาจากฟอร์ม — ต้องยืนยันจาก session ฝั่ง server เสมอ
